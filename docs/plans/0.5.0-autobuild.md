# Plan: the Studio builds 0.5.0 itself, and proves it

> Addendum to [0.5.0-plan.md](0.5.0-plan.md). The approved plan keeps the scope,
> the decisions and the status board; this file is the loop the Studio follows to
> finish that board and verify it. Hand-offs go in `continuing.md`, newest first.

## Goal

Every item on the 0.5.0 status board is either **landed on `main` and verified**,
or **listed as owner-only with the exact step** needed. "Verified" has a
definition below, not a feeling.

## Source of truth

1. `docs/release-scope-0.5.0.md`: what 0.5.0 includes, and the "Try by hand" lists.
2. `docs/plans/0.5.0-plan.md`: the status board (section 1) and the landing method (section 3).
3. `continuing.md`: what was done last, what is in progress, and what is waiting on the owner.
4. `TESTRUNS.md`: one row per validation run, newest first.

If these disagree, the newer dated entry wins and the disagreement is recorded in
`continuing.md`.

## Permissions

| Action | Allowed |
| --- | --- |
| Work in a worktree or a `wip/<topic>` branch | Yes |
| Fast-forward `main` through `npm run sync` after `npm run check` passes | Yes (approved in 0.5.0-plan.md, decision 2) |
| Force-push, or any history rewrite on `main` | Never |
| `npm run package*`, a `v*` tag, a `workflow_dispatch` release, a `gh-pages` publish | **No**, owner only, at release time |
| Discord, relay deploy, GitHub secrets or Friends sign-in | **No**, owner only |

## The loop

Repeat until the board is green or the stop rule fires.

1. **Pick** the next open row on the status board, in plan order (landing before
   new features). Skip any row that needs the owner.
2. **Isolate**: a worktree off `origin/main`, on `feat/<topic>` or `land/<topic>`.
   Never work in a shared checkout that another session is using.
3. **Build** the smallest change that closes the row. Follow `AGENTS.md`: classic
   scripts, no new dependencies, the four registration points for a new renderer
   file, `npm run build-booklet` after renderer edits.
4. **Test** the change with its own suite first, then the related suites, using
   `npm run test:one -- tests/<name>.test.mjs`. Never a bare `node --test`.
5. **Gate**: `npm run check`, then `npm test`, then `npm run audit`, all on the
   exact commit that will land.
6. **Record**: one TESTRUNS row via `node scripts/append-testruns-row.mjs`, and a
   line in `continuing.md`.
7. **Land**: fetch again, fast-forward into `main`, run `npm run sync`. Never skip
   the check to get a push through.
8. **Verify on Windows** when the row needs it (see "Verified" below). Linux CI
   failures that are known environmental (TESTRUNS "Known environmental failures")
   are recorded, not hidden.

## What "verified" means

A row is **verified** only when every item that applies to it is true:

- **Automated:** its suite passes on the landed commit, and `npm test` shows no
  new failures against the last known-good run.
- **Behaves in the real app:** for UI rows, a fresh-profile run of the built app
  shows the change at 1920×1080 and at 600×560, in both themes, with a screenshot
  captured from the app (not a mock-up).
- **Survives restart:** for any setting, it still holds after a relaunch
  (owner rule: every toggle comes back).
- **Two-PC rows** (Friends, Your PCs, handoff, resource manager) need two Studios
  (two windows on separate profiles is the minimum, a second PC is the full check).
  A single-window test does not verify them.
- **Owner-only checks** from release-scope-0.5.0.md's "Try by hand" stay listed as
  unverified until the owner ticks them. They are not counted as done.

## Stop rules

Stop and write a `continuing.md` entry (do not guess) when:

- a gate fails for a reason outside the change, and the failure is not in the
  known-environmental table;
- a change needs a decision the owner has not made (see "Decisions" in
  release-scope-0.5.0.md);
- the lease shows another session holds the test turn for longer than one suite;
- a push would leave out 200 or more lines of another branch's work (`npm run sync`
  refuses this; do not override it with `--allow-lost-work` without the owner).

## Owner-only list (never automated)

These block the release and are listed for the owner, with the exact step:

1. One real Sign in with Discord, and the Discord user IDs of moderators.
2. Publish PC-only branches (`feat/devday-2026`, `overhaul/phase2`, `C:\wt\*`) as `wip/*`.
3. The attended "Try by hand" checks in release-scope-0.5.0.md, on a real display.
4. Relay redeploy (`relay/README.md`, "Deploying").
5. The release decision, the version bump and `docs/releases/0.5.0.md`.
6. Which model roles the Studio uses (see the open question in `continuing.md`).

## Done means

- Every status-board row is landed, verified or owner-listed, with a TESTRUNS row each.
- `npm run check`, `npm test` and `npm run audit` pass on `main` with no new failures.
- `continuing.md` reads as a complete hand-off: what was done, what was verified,
  what is waiting, and why.
