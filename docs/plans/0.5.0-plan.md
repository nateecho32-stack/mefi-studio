## 2. Framework decision: **stay on Electron 44 for 0.5.0**, and keep leaving cheap

**Answer to "move over or finish first?":** no move is needed, so finish everything on Electron. The hedge is to keep the engine independent of the window.

| Your need | What the code does today | Why Electron is enough | What moving would cost |
|---|---|---|---|
| **Load times** | 81 CJS modules (1.36 MB) `require`d synchronously, sync `settings.json` read, no compile cache/snapshot/asar, 5 MB inline booklet, deferred timers at +1.5…+8 s. Measured (dev, Windows): composer usable ~0.82-0.95 s, smoke ~2.65-2.7 s. **No cold-start or RAM baseline exists.** | The slowness is app-side and fixable in place. Electron 44 already has faster `utilityProcess`/child fork (82→37 ms) and a renderer code cache | Tauri's published benchmarks (0.5-1 s vs 2-4 s cold, ~45 vs ~180 MB idle, 3-10 vs 120-200 MB bundle) measure small sample apps, not one with a 23k-line Node engine. That engine would still run, in a Node sidecar |
| **Peer co-work** | One outbound WebSocket per PC to a "rooms hub" on one PC behind a Cloudflare tunnel; Discord identity; cowork = per-file path leases; multi-PC sync = sealed vault in a private GitHub repo. **No WebRTC, no P2P** | The transport is a library choice, not a framework one. **iroh** (QUIC, hole punching, relay fallback, Node bindings that run in Electron's main process) can add direct links later | Same library works in Rust, so no advantage for moving |
| **Agent handling** | Builders are child processes supervised on the single main-process thread; admission reads renderer frame lag via `executeJavaScript` (needs a live window); scripts run under `ELECTRON_RUN_AS_NODE` | Move supervision + board writes to `utilityProcess` behind the existing row-delta messages; decouple admission from the window | A Node sidecar anyway, or a Rust rewrite of 52k lines of `scripts/` |
| **Electron-only features in use** | `desktopCapturer` loopback audio (music-reactive tree), `WebContentsView` media browser, YouTube Referer hook, `capturePage`/offscreen capture (tests, screenshots, before/after evidence), 17+ Electron fixtures, 161 of 398 test files slice `main.cjs` | Keep | Each needs a native rewrite plus a new harness (tauri-driver + msedgedriver); the bespoke updater + safety net just built would be replaced |

Facts that make the current code cheap to keep portable: only **2** production `require('electron')` sites, **0** of 143 `scripts/` import Electron, 37 modules (15.2k lines) are enforced pure, Electron symbols are 2.1% of `main.cjs`. There is **no WebGL** (all 10 canvas contexts are 2D), so WebView2's GPU limits would not bite; the GPU cost is Canvas2D filters + CSS effects, which the tree-brightness fix targets.

Other candidates (Electrobun, Deno Desktop, Wails v3) are young; in 2026 the serious choices are Electron and Tauri.

**Do inside Electron (in order):**
1. **Measure first** (Phase 0): land S1 startup marks, run `tools/benchmark_startup.py` on the PC for cold start, time-to-usable, idle RAM/GPU. Existing budgets: usable within 150 ms of ready; frame mean ≤6 ms, p95 ≤10 ms.
2. Cheap levers: lazy-require non-boot modules; bundle `main.cjs` for packaged builds only (dev/vm suites keep slicing the source); `module.enableCompileCache()`; move the remaining sync boot I/O behind the settings cache (S1); trim the deferral chain.
3. Agent handling: admission uses main-thread event-loop delay when no window; stage the supervisor into a `utilityProcess` only if measured lag with 6 builders justifies it (post-0.5.0 otherwise).
4. Peer transport: Friends 2.0 keeps the hub for Discord identity and rooms; add an optional direct iroh link for Your PCs in 0.5.x.

**Revisit triggers:** Electron/Chromium launch stays >50% of time-to-usable after (2); the ~110 MB download/update becomes a real complaint; macOS/Linux ports need native webviews; or the engine has been split into a sidecar (then a shell swap is a spike). Spike design: same renderer + Node sidecar under Tauri; success = ≥40% faster time-to-usable and ≥50% less idle RAM, with loopback audio and the media browser ported in ≤2 weeks.

### 4.2 Architecture: **one shell, evolved by region, on the existing nav registry**
- This is your Fleet plan's **Phase 5 plus the menu overhaul, done as one piece**: the same regions (persistent inspector, status bar, buckets bar, **+ Add panel**) and the same rules: no second shell, no new `uiMode`, no new navigation system, zero new dependencies, classic scripts, land on `main` continuously so nothing repeats the lost `7ba162c` merge.
- **Same rail shell, same `nav.js` route registry.** The tab strip, session list and inspector are *views over existing routes* (a tab = registry route + params), so there is still one navigation system and old deep links still redirect (`commit-check` rule 7). New regions arrive one at a time behind a layout switch, `mefiStudio.layout = v1 | v2` (setting + `?layout=`): default `v1` until the release candidate, flipped at 0.5.0. **Recommendation:** delete the v1 chrome one release later (0.5.1), not at 0.5.0, so there is an escape hatch. Route pins and the reachability suites (`app_rail`, `nav_startup`, `palette_keyboard`, `unified_studio_render`) must pass throughout.
- **Never add a third `data-shell` value; use a second attribute, `data-layout="v2"`, and keep `data-shell="rail"`.** `data-shell` has one writer (`applyShell`, `nav.js:1723`), classic is its absence, and every JS gate tests `=== "rail"` (`nav.js:769,785,1604,1825`, `sidebar.js:30`), so a new value would silently behave as classic and start matching four `:not([data-shell="rail"])` rules. Vibe is the working precedent: it keeps `data-shell="rail"` and overrides (`vibe.css:612-615`). Tests pin the boolean (`app_rail`, `nav_startup:26`, `vibe_frame:98`, `git_sync_ui:206`).
- **This is not a skin; it is a layout contract (first Phase 1 job).** Pages are viewport-fixed layers: the 11 `WORKSPACE_PAGES` (`nav.js:768`) sit at `inset: var(--shell-local-h) 0 0 var(--shell-rail-w)` (`styles.css:5086`), tab pages toggle `hidden`, views are full-window. Two variables are the whole host contract, with no right or bottom inset. So: add `--shell-list-w`, `--shell-inspector-w` and `--shell-status-h` insets, consumed once by the ~10 fixed containers (`styles.css:5048-57`); update the ~9 scripts that read the rail rect (`idle.js:4055`, `media-window.js:135`, `companion-ui.js:313`, `git-sync.js:1572`, `workspace.js:153`, and the orb re-parent at `agent-brain.js:1515`); keep the rail at 64/256 px (`workflow-render-electron.cjs:193` pins it, so the prototype's 68 px becomes 64). Grid re-parenting of existing pages without touching their CSS does not work.
- **Small windows are a hard constraint:** the minimum window is 600×560 (`main.cjs:22641`) and fixtures test 600×560 at 150% zoom, about 400 CSS px. Rail + list + tab strip cannot fit, so the list column and inspector fold into drawers (the prototype's `.frame.narrow` pattern) and tabs collapse into a menu below ~900 px.
- **One panel contract**, the one your Fleet plan named: `renderer/panels.js` (`MefiPanels`) plus `ui-kit.js`, built by evolving builder-mode's `MefiPanes` (docks, pops out into movable and resizable windows, closes, persists, and moves the element so drafts, scroll and open disclosures survive). Every new or rebuilt view is a panel: it mounts as a tab now and docks as an inspector region. Add a tiny keyed patcher `patch.js` so pushes never rebuild focus, scroll, drafts or `<video>`/iframe nodes (the prototype re-renders with `innerHTML` and hand-restores scroll and focus, `render()` at its line 1716, which cannot keep a playing video). No DOM diff helper exists today (house style is rebuild plus a signature gate, `nav.js:65-67`; `MefiMotion.keep`, `motion.js:109`, and the hand-rolled reconcile at `nav.js:1457-1487` are the nearest), so `patch.js` extends that keyed idea. There is also **no splitter helper**; the only pointer-capture drag code is `media-window.js:316-358` (with arrow keys), `companion-ui.js:276` and `fleet.js:409`, so column splitters inside `panels.js` (`--dock-*` offsets) start from that.
